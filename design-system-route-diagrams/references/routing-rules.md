## 几何单位

在 2100 × 1200 的参考画布上使用 `u = 8 px` 作为基础单位。使用其他画布尺寸时等比例缩放全部数值。

| 元素 | 规范 |
|---|---|
| 组内轨道间距 | `1u` |
| 组间走廊间距 | `2u–3u` |
| 与无关节点的净距 | 至少 `1u` |
| 与文字轮廓的净距 | 至少 `1u` |
| 转角前最短直线段 | `2u` |
| 节点圆角 | `1.5u` |
| 彩色主线 | `1.8 px` |
| 白色线晕 | `3.6 px`、50% 透明度 |
| 节点边框 | `1.35 px` |
| 单行节点高度 | `6u` |
| 双行节点高度 | `7u` |
| 高负载中间件高度 | `10u–12u` |

保持同一组的轨道间距恒定。不得通过逐步压缩线束来适应空间；应增大或移动承载节点。

## 共享拓扑骨架

先建立每个面板的规范节点表和唯一节点骨架，再安排线路。不同名称若指向同一进程、服务、设备或系统，应归并为同一规范组件；调用方、服务方等角色差异不自动产生新节点。复合显示名、括号角色和 route/端口差异本身不足以证明存在多个组件，默认先归并为别名；只有事实明确声明独立运行实体时才拆分。事实明确命名但未说明宿主进程的业务能力，可以作为逻辑服务节点进入服务层，节点只表达能力端点，不宣称部署归属。

使用以下构图顺序：

1. 将承担全局入口、连接多条主链路的主要调用者或上游系统放在顶部；不要把每条线路的起点都自动归为顶层调用者。
2. 将接入、桥接和通信组件放在其下方或视觉中心。
3. 将适配、端点或协议转换组件放在桥接层下方。
4. 将编排、调度或执行组件放在中下部。
5. 将内部服务放在底部同一层；只连接少量中间组件的单用途工具、状态源、外围端点、侧向接入者和对等模块放在主要邻接层旁侧。
6. 对同时承担上游和下游角色的组件只放置一次，以回向线路表达反向调用。

这是默认骨架而非业务模板；可以省略不存在的层级，也可以根据事实调整同层顺序。不得为了减少弯折而改变组件的实际层级。

从全部线路共同推导层级，而不是逐条推导：统计组件对在主调用路径中反复出现的先后关系，以占主导的顺序建立纵向层级；少量反向消息用回向线路表达。若桥接组件和适配组件在多条主链路中持续呈现“桥接 → 适配 → 编排”的顺序，应放在连续的上下层，不要横向并排。

顶层空间优先给高连接度、承担多条主调用的主要入口。低连接度的单用途端点优先靠近其第一个共享邻接组件放在侧边；这既保持层级语义，也减少贯穿整图的长回线。

若一个低连接度端点通过同一桥接组件存在两条方向相反的线路，将它按桥接层对等端点处理，放在桥接节点侧边，并为两个方向分配上下或左右两条平行轨道。不要仅因其中一条线路把它写成终点，就将其放到底部服务层。

当多条线路共享任一组件时，优先绘制一张共享拓扑图。语义分组是不可见的空间规划，不是可见泳道：不要为每条线路或每个分组重复组件、添加整套节点，或把主图变成横向链路清单。只有彼此没有共享组件、确属独立系统的子图才适合分区展示。

传输协议、route、topic、消息类型和状态文字默认作为线路或端口元数据，放入图例、节点副标题或简短线路标注；不要把它们画成胶囊节点。即使事实源把 `A → WebSocket → B` 写成箭头序列，只要没有证据说明 WebSocket 是独立部署进程，也应将其归为 A 与 B 之间的传输标注。

对每条线路同时读取标题、箭头表达和正文说明，分别确定调用方、基础设施跳点与业务服务方。保留事实项标题作为短名称；标题已经明确“调用/Call/Invoke 服务、技能或能力 S”而箭头只写到编排组件时，若事实没有正面限定为接入段视图，应将 S 作为 `named_target` 和逻辑服务终点补入同一条端到端路径。不要把基础设施链路的简写长度或下游进程信息缺失误当成业务调用边界，也不要因为 S 的宿主进程未知而删除这个已确认的逻辑端点。

## 走廊构建

1. 确定主流向；调用图优先使用从上到下。
2. 为每个语义组分配独立的走廊矩形；走廊是布局规划区域，不绘制成包含重复节点的可见分组框。
3. 按调用方/服务方角色排列分组，不按线路编号或颜色排列。
4. 在走廊内以严格 `1u` 间距分配轨道。
5. 在线路共同经过的全部区段保持轨道顺序不变。
6. 将分组入口、出口和转角坐标吸附到 `u` 网格。

使用以下模式：

| 关系 | 走线模式 |
|---|---|
| 同组、同方向、共享节点 | 平行总线 |
| 不同组、共享节点 | 独立走廊，间隔 `2u–3u` |
| 相同节点、方向相反 | 使用共享节点或走廊的两侧 |
| 同层节点交互 | 水平双线或线束 |
| 横向和纵向走廊相交 | 固定正交井字交叉 |
| 同时展示请求和响应 | 两条单向轨道 |

密集共享节点内部不得完全依赖自动路由器。必须显式设置端口、内部轨道和路径点。

主流向为纵向时，高负载共享节点应沿横向加宽，为平行的纵向轨道提供端口带；主流向为横向时则沿纵向增高。不要仅沿主流向放大节点，否则线路会集中在狭窄边缘。

## 连续路径与节点穿越

一条逻辑链路只使用一个最终可见 path。路径从起点边框开始，连续穿过有序中间组件，在终点边框结束。可以用逐跳边辅助自动布局，但正式 SVG 必须移除这些断开的边，并叠加一根连续的正交路径。

- 按稳定的分组顺序分配边缘端口。
- 现状和目标侧的对应节点使用相同端口顺序。
- 起点和终点只连接线框边缘，不把可见端点放在线框内部。
- 中间组件不是线路端点：路径应进入节点、沿内部空白轨道连续通过，再从另一边离开。
- 纵向流量优先从上/下边缘进入；同层流量优先从左/右边缘进入。
- 在中间件节点内部预留空白轨道。水平轨道放在文字上方或下方，纵向轨道放在文字两侧。
- 多个语义组穿过同一节点时，为每个组分配独立轨道带。
- 允许线路穿过节点背景，但不得穿过文字轮廓。
- 不要为 route 名单独创建线框节点；将 route 信息放在节点副标题或图例中。

## 交叉与转角

- 只使用曼哈顿路径。
- 将相邻线路的转角对齐到相同网格行或列。
- 每个语义组优先使用一条公共转角基线，并保持各轨道平行。
- 避免节点附近的阶梯形扇出；将其改造成矩形井字结构。
- 在每条彩色线路下绘制白色线晕，使交叉线路仍保持独立。
- 普通交叉不得绘制连接点。
- 只有数据模型明确声明合并或分叉时才绘制连接点。
- 编号与转角、箭头至少间隔 `1u`。相邻轨道的编号发生接触时错开编号位置。
- 每条逻辑链路在每个适用面板中只设置一个编号徽标；一个编号下存在多个 topic 或消息类型时，将它们写入图例或元数据，不复制线路和徽标。

## 图层顺序

按以下顺序绘制，使线路经过共享节点时既连续又可读：

1. 面板和分层背景。
2. 节点填充。
3. 线路白色线晕和彩色主线。
4. 节点边框。
5. 节点文字、线路编号和箭头；文字必要时增加窄白色描边。

不要把线路全部压在节点下方，否则经过中间组件时会看起来断开。也不要把文字压在线路下方；优先移动内部轨道到文字上方、下方或两侧留白区。

## 迁移对比

使用 2100 × 1200 的参考画布：

- 顶部标题区约 `80 px`。
- 左右面板等宽，各约 `1015 px`。
- 中间使用蓝色竖向虚线分隔。
- 两个面板下方使用一套全宽共享图例。

走线前建立节点对应表：

```yaml
node-map:
  stable-node:
    current: node-a
    target: node-a
  removed-node:
    current: node-b
    target: null
  new-node:
    current: null
    target: node-c
```

应用以下规则：

- 先综合全部规划决定组件安置：职责全面迁走且没有目标链路明确保留的共享旧组件标为 `retired`，不得出现在目标节点或目标线路中。单条规划的细节缺省不能推翻全局退役结论。
- 以现状线路的有序节点序列作为目标线路初稿，再逐项应用迁移事实中明确的节点增加、替换和删除。目标说明省略细节不等于删除；没有明确变化依据的中间节点继续保留。
- 将不变节点放在对应坐标。
- 必要时为拆除或新增节点设置不可见的层级/间距锚点，以保持两侧对齐。
- 只有语义身份相同的线路才能沿用相同颜色和编号。
- 拆除线路只绘制在现状侧，新增线路只绘制在目标侧。
- 线路消失只影响线路本身；仍标为 `retained` 的端点组件继续按普通节点绘制。不要用虚线节点、灰色幽灵或删除遮罩暗示组件也被拆除。
- 不得为了让旧线路视觉连续而伪造目标侧区段。
- 多条旧线路收敛为一种目标行为时，只绘制已经确认的目标线路，并在图例或事实表中说明收敛关系。
- 若文档明确某项业务仍调用同一服务，只迁移传输、route 或中间承载组件，则保留已确认的调用方和服务方，替换明确变化的路径区段。只有服务端点或后续拓扑确实未给出时，才把线路画成未闭合状态。
- 目标侧已定义清楚的规划路径使用实线；不要因为它尚未实施就自动改成虚线。虚线只表达悬空、待确认或目标拓扑未闭合。
- 尽量保持未变化线路的几何形态一致，让视觉差异集中体现真实迁移。

## 校验条件

出现以下任一情况时拒绝交付：

- 线路的有序节点序列与事实契约不同。
- 一条线路同时属于两个语义组。
- 两条彩色线路共享可见线段。
- 线路穿过无关节点。
- 线路终止于节点内部，而不是节点边缘。
- 同一组在线路中途交换轨道顺序。
- 组内间距偏差超过 10%。
- 组间距没有明显大于组内线距。
- 未声明合并的交叉看起来像连接点。
- 迁移图中的对应节点无语义原因地发生位置漂移。
- 目标线路删除了现状中间节点，却没有登记明确的迁移依据。
- 目标侧仍显示已登记为退役的组件或经过该组件的线路。
- 保留组件因为某条线路拆除而被画成幽灵节点或从目标侧消失。
- 同一事实编号因包含多个 topic 或消息类型而被拆成多条线路。
- 标题或正文已明确的实际服务端点因为箭头简写而从拓扑中遗漏。
- 端到端线路的最终节点与登记的业务服务方不一致。
- 事实已命名的调用目标因为宿主进程未知而被省略，或被无依据地归属到某个部署组件。
- 同一系统因为复合显示名、角色文字或 route/端口不同而被拆成多个节点，却没有独立运行实体的事实依据。
- 可见线路缺少编号徽标，或同一线路在一个面板中出现多个编号徽标。
- 同一规范组件在单个面板中出现多个可见副本，但事实没有声明多实例。
- 传输协议、route、topic 或消息类型被误画为独立组件节点。
- 共享组件的线路被拆成按线路或分组排列的独立流程行。
- 一条逻辑链路由多个互不连接的可见 path 拼成。
