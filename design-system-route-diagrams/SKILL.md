# 系统链路图设计

绘制视觉优化不改变链路事实的精确架构图。使用固定的视觉语言和路由体系，同时保留对语义分组和节点位置的判断空间。

## 建立事实源

绘图前登记规范组件和每条线路：

```yaml
components:
  - id: canonical-component-id
    aliases: [alternate-name]
    kind: runtime-component | logical-service | device | system-boundary
    layer: caller | ingress | adapter | orchestrator | service
component_disposition:
  canonical-component-id: retained | retired | new
routes:
  - id: route-id
    short_name: preserve the fact-item title
    group: semantic-group
    panel: current | target | both
    nodes: [caller, middleware, orchestrator, provider]
    named_target: canonical-target-id | null
    provider: canonical-provider-id | null
    scope: end-to-end | ingress-only | egress-only
    scope_evidence: required when scope is not end-to-end
    migration: {removed_nodes: [], added_nodes: [], evidence: required for changes}
    direction: forward
    status: active | pending | suspended | removed
    style: solid | dashed
    metadata: {transport: optional, route: optional, topic: optional, message: optional}
```

先建立规范组件表，将别名和不同角色称呼归并到稳定的组件 ID。进程、服务、设备、明确的系统边界，以及被事实源明确命名为调用目标的业务能力，都可以成为节点。宿主进程未知的具名能力登记为 `logical-service`：只表达逻辑服务端点，不暗示其部署归属。传输协议、route、topic、消息类型和状态说明属于线路元数据，除非事实明确把它们定义为独立部署组件，否则不得画成节点。链路文字中的 HTTP、WebSocket、gRPC 等传输词默认标在线路上，不因出现在箭头序列中就成为节点。

复合显示名、角色后缀和 route 名不自动产生新组件。`A`、`A / 某角色`、`A（调用方）`默认先作为同一规范节点的别名审查；只有事实明确说明它们是独立进程、设备或系统边界时才拆分。不同 route 或端口连接到同一系统，也仍然复用同一节点。

将 `nodes` 视为只包含规范组件 ID 的有序契约。不得为追求美观而增加、删除、合并、重排或猜测节点。先澄清不确定的拓扑，再进行视觉设计。

以事实项或编号作为逻辑链路身份：同一编号下列出的多个 topic、消息类型或简单桥接默认是同一条业务链路的元数据，不自动拆成多条彩色线路。

为每条线路分别确认技术箭头和业务端点，并用事实项标题原文或等价短标题填写 `short_name`。标题或正文只要明确写出“调用/Call/Invoke 某服务、技能或能力”“由某服务提供”或等价关系，就必须登记 `named_target` 和 `provider`；如果只知道能力名而不知道宿主进程，就创建同名 `logical-service`，不得把它擅自归属到某个进程。对于具名目标和其他 `end-to-end` 链路，`nodes` 的末项必须是该服务，即使正文中的箭头简写停在桥接器、端点或编排器。

“没有写出下游进程”“箭头只写到编排器”属于信息缺省，不是限定图示范围的证据。只有事实源正面说明“仅展示接入段/上行段/本段”或等价含义时，才可使用 `ingress-only` 或 `egress-only` 截断具名调用；否则具名调用必须以逻辑服务闭合。

当图中超过三条线路或使用 `migration` 模式时，将上述事实表保存为 JSON，并在绘图前运行 `python3 scripts/validate_fact_manifest.py <manifest.json>`。校验失败时先修正事实建模，不得跳过、降低为仅几何校验或继续交付。

严格区分以下概念：

- **语义分组**：调用方/服务方角色以及消息性质相同的线路集合。
- **视觉走廊**：为某个语义组预留的横向或纵向空间。
- **独立轨道**：一条可以从头到尾独立追踪的彩色线路。

不得仅因经过相同节点而合并分组。不得仅因共享走廊而合并线路。

## 选择绘图模式

单一架构状态使用 `single`。请求涉及现状/历史与目标/未来对比，或涉及替换、拆除、合并、迁移时使用 `migration`。

`migration` 模式必须遵守：

- 在处理单条线路前，先根据全部规划建立组件安置表。若一个共享旧组件的各项职责都被迁移、替换或拆除，且没有任何目标项明确继续使用它，将其登记为 `retired`；目标侧不得因某条规划描述省略细节而重新画回退役组件。新增组件登记为 `new`，其他为 `retained`。
- 左侧放置现状/历史，右侧放置目标/未来。
- 两侧面板等宽等高，使用竖向虚线分隔。
- 两侧共有节点保持相同尺寸、层级、顺序和相对位置。
- 目标侧不显示已拆除或 `retired` 节点和线路；必要时使用不可见间距锚点保留其布局层级，避免其他节点跳位。
- 组件安置与线路安置相互独立：某条线路被拆除或并入，不代表其端点组件被退役。`retained` 组件在目标侧继续使用普通实线边框，不因暂时没有独立线路而画成虚线、灰色幽灵或删除占位。
- 新增节点和线路只显示在目标侧；有利于对齐时，在现状侧预留对应空间。
- 只有业务语义相同的线路才能沿用相同编号和颜色。
- 为每条目标线路先复制其现状有序节点序列，再应用事实源明确声明的增加、替换和删除；不要从空白重新猜测目标链路。迁移说明未提及的中间节点默认保留，不能因目标描述较短或入口细节未展开而删除。
- 未变化线路在两侧保持相似几何形态，只修改迁移影响的区段。
- 通过“目标侧缺失”和图例表达拆除；除非用户明确要求，不添加叉号或删除遮罩。
- 当迁移说明只替换传输、route 或中间组件，且业务调用方与服务方保持不变时，保留已确认的两端，只替换明确变化的区段；不要把迁移后的链路截断在传输元数据上。
- 目标侧中已经定义清楚的规划链路使用实线；目标面板本身已表达“未来”。虚线只表示悬空、待确认或拓扑尚未闭合的线路。
- 禁止绘制跨越中间分隔线的箭头。

## 建立语义分组

按以下证据优先级分组：

1. 调用方和服务方角色。
2. 调用、回调、广播、遥测、状态或同步等消息性质。
3. 主消息方向。
4. 协议或消息模型。
5. 业务能力。

即使经过相同组件，也要将调用方发起的能力调用与服务方接入框架分成不同组。将状态、广播链路与技能/RPC 链路分开。

## 形成整体构图

先画共享组件骨架，再叠加线路。除非事实明确存在多个实例或系统边界，同一面板中的同一规范组件只绘制一次；组件承担多个角色时也复用同一节点，通过进出方向表达角色变化。

语义分组只用于规划总线走廊、端口和轨道顺序，不为每个分组复制组件或建立一套独立流程子图。当两条以上线路共享组件时，不得把主图展开成“每条线路一行”或“每个分组一块”的链路清单。先形成清晰的系统层级和主调用方向，再根据实际拥挤程度灵活调整节点位置、线路弯折和间距。

在迁移场景中，现状与目标尽量保持共有组件的位置和层级一致，使读者首先看到链路如何迁移，而不是两张不同布局的流程图。

## 安排节点

- 默认让主调用方向从上到下。
- 在事实允许时，按调用方、接入/中间件、编排和服务分层。
- 根据组件在多条链路中的稳定架构角色和反复出现的先后关系确定层级，不要简单把每条线路的第一个节点都当成顶层调用方、最后一个节点都当成底层服务。
- 若两个共享组件在多条主链路中反复以固定顺序相邻出现，优先放在连续的上下层，而不是为了少弯折将它们横向并排。
- 将同级调用方或服务方放在同一层。
- 顶层优先保留承担全局入口或参与多条主链路的主要调用者。将只连接少量中间组件的单用途工具、状态源、外围端点、伴随服务或对等模块放在其主要接入层旁侧，不要仅因它是某条线路的起点或终点就放到最上层或最下层。
- 若某低连接度端点通过同一桥接组件形成两条方向相反的请求/回报线路，将它视为桥接层对等端点，优先放在桥接组件侧边，而不是底部服务层。
- 某组件同时承担上游和下游角色时，按整体架构中的稳定位置放置一次；反向链路通过回向线路表达。
- 将高频经过的中间件放在视觉中心附近。
- 线路过多时沿轨道展开方向扩大节点：主流向纵向时优先加宽高负载节点，主流向横向时优先增高；不要压缩轨道或穿过文字。
- 保持节点名称简短；仅在需要区分时，将 route 或传输信息放在第二行。
- 将可见线路端点连接到节点边缘，不得连接到悬空点。

## 绘制线路

当图中超过三条线路、存在共享中间件或需要迁移对比时，必须读取 [references/routing-rules.md](references/routing-rules.md)。

遵守以下不变量：

- 只使用水平线、垂直线和 90° 转角。
- 将一条逻辑链路绘制成一根从起点到终点的连续路径，按顺序穿过全部中间组件；不得把逐跳边裁剪成相互断开的线段。
- 每个语义组分配一条独立走廊。
- 组内线路保持平行、等间距，并从起点到终点维持相同顺序。
- 组间距必须大于组内线距。
- 将相似转角对齐到公共网格，形成整齐的总线和井字结构。
- 不得让彩色线路共用或重叠同一线段。
- 普通交叉表示不连接：使用白色线晕，不绘制连接点。
- 起点和终点连接在线框边缘；中间组件使用连续的内部轨道穿过。线路经过节点时，只能使用文字上方、下方或两侧预留的空白区域。
- 使用“面板背景 → 节点填充 → 线路白色线晕与彩色主线 → 节点边框与文字”的图层顺序；必要时为最上层文字添加窄白色描边。
- 将线路编号放在远离转角和箭头的独立直线段上。
- 除非用户明确要求响应方向，否则只展示主请求/消息方向。需要展示两个方向时使用两条单向线路，禁止使用双向箭头。

## 应用视觉系统

使用 [assets/style.json](assets/style.json) 作为默认视觉契约。

- 使用白色画布、浅蓝色现状面板和浅绿色目标面板。
- 使用蓝色圆角节点、近白色填充和深蓝色文字。
- 按色板顺序为线路分配稳定且可区分的颜色。
- 在较宽的半透明白色线晕上绘制较窄的彩色主线。
- 图中只放线路编号；完整说明统一放在两侧面板下方的共享图例中。
- 每条可见逻辑链路在其所在面板内放置且只放置一个编号徽标。图例使用“编号 + 短名称”的紧凑条目，详细路径和消息说明保留在事实文档中，不通过增高画布塞入长段文字。
- 虚线只表示悬空、待确认或明确非活动状态，并在图例中解释。
- 默认遵守 `style.json` 的画布尺寸；优先压缩图例文案和留白，不为容纳说明随意增加画布高度。
- 优先使用确定性 SVG，或使用 Graphviz 布局后再处理 SVG。禁止使用生成式图片作为正式拓扑图。

## 交付前校验

执行全部检查：

1. **实体**：确认协议、route、topic 和消息类型没有被误画为组件；确认具名业务能力在宿主未知时被标为逻辑服务而非伪造部署组件；确认每个规范节点在单个面板中只有一个可见实例，明确的多实例除外。
2. **拓扑**：根据事实表的逻辑编号核对每条线路的起点、有序中间节点、业务服务端点、方向、编号和状态；每条逻辑链路必须是一根连续可追踪的路径，同一编号的多个 topic 不得被误拆线。标题含调用意图时必须登记 `named_target`；对具名目标和每条 `end-to-end` 链路断言 `nodes[-1] == provider`，正文明确的服务端点不得因箭头简写而遗漏。
3. **分组**：确保每条线路恰好属于一个语义组，且分组没有演变成重复节点的独立流程子图。
4. **几何**：拒绝误穿无关节点、共线重叠、斜线以及位于节点内部的起止端点。
5. **走廊**：核对组内等间距、较大的组间距、对齐的转角和稳定的轨道顺序。
6. **迁移**：先核对组件安置表，再核对不变线路身份和节点位置、仅现状侧存在的拆除项、仅目标侧存在的新增项；目标线路不得包含退役组件。逐条比较现状与目标节点序列，确认每个增删节点都有明确迁移依据，未提及且未退役的节点没有因目标描述简短而消失。
7. **状态样式**：已闭合到 provider 的规划链路使用实线；只有悬空、待确认或未闭合拓扑可以使用虚线。保留组件不得因相关线路被拆除而改变成幽灵样式。
8. **标识与追踪**：每条可见逻辑链路在每个适用面板中恰有一个编号徽标；从徽标沿同一根线追踪到箭头，依次经过事实表中的全部组件，不得依赖颜色变化、猜测或隐含连接。

将 SVG 作为正式源文件，PNG 只用于审阅。按“拓扑、走线、装饰”的顺序迭代。
